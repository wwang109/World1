# Community service

Scope: read-only GitHub intake, private account wallets/support, UTC rounds, protected merger configuration, and release evidence. Runtime content ingestion is documented in `architecture.md`, Community content snapshots.

The public source is `wwang109/wandering-hand-content`, repository ID `1426486653`. `GET /community/proposals` and `/community/proposals/:number` expose imported public snapshots with their exact head SHA and source check time. `POST /community/import` accepts a canonical PR URL and requires a game bearer session. There is no upload, PR publisher, client point grant, or merge endpoint. Source outages retain visibly dated snapshots and prevent new support spending. A successful receipt can still be recovered during a source outage.

Use `npm run api` with Vite. The file service uses `.tmp/eligible-community-state.json` unless `ELIGIBLE_COMMUNITY_STORE_FILE` overrides it. Canonical runs and community data share one serialized transaction coordinator and one atomic file replacement. Run one development API process per state file. Invalid persisted JSON fails closed; never replace it with an empty wallet. The file is local private account data and must not be published.

`npm run api` and `npm test` first run their npm preparation hooks: offline `content:verify`, then `build:run-executors`. This reconstructs ignored generated executor files, including the small `generated/current.json` used by runtime identity, on a clean checkout and after source edits. Preparation does not fetch GitHub or approve a registry entry. The existing test gate runs after preparation. Use the npm commands so a direct server launch does not reuse a stale or missing generated executor; retained contexts remain in the generator's registry.

Production Pages routes require `GHOSTS_DB`. Apply migrations `0003_community.sql`, the canonical-run migration `0004_eligible_runs.sql`, `0005_community_points.sql`, and `0006_voting_rounds.sql` through the existing D1 deployment process. Confirm the actual migration filename in `migrations/` before executing. D1 `batch` owns the entire canonical encounter/run/ledger/wallet commit. Ledger UPDATE and DELETE are rejected by database triggers. Operational corrections are appended with reason, moderator identity, and their own operation receipt. Closing a proposal does not refund support.

Apply `0007_community_backups.sql` before running the backup-gated merger. It adds immutable backup receipts keyed by round and unique operation ID; UPDATE and DELETE fail. Private `/community/me` returns `canModerate` and bounded review capabilities from the authenticated account's linked-provider status and deployment allowlist. The browser cannot grant itself that role. `GET /community/rounds/:id` returns a frozen round and its public backup manifest/digest when present.

Apply `0008_community_source_sync.sql` for scheduled intake. Every Worker cron performs bounded read-only reconciliation before closing rounds. A durable lease prevents duplicate schedulers from multiplying requests; its pending keys/cursor survive restarts, and the recent five PRs are checked independently of historical backfill. Default limits are one proposal every fifteen minutes without a reader token, or five every five minutes with one; `COMMUNITY_SOURCE_SYNC_BUDGET` may set 1–10. Known immutable head bytes are reused while current source metadata is confirmed. Proposal/draft manifests stay at 256KiB; canonical runtime JSON may be up to 8MiB per file, with a 40MiB read batch limit. This accommodates the actual skills/events catalogs.

Source failures persist a visible status and at least fifteen-minute backoff. Invalid proposals suspend old review/readiness instead of leaving a stale candidate eligible. A round cannot close until supported eligible cached proposals have been source-checked after its deadline; source outage or unfinished confirmation delays closure and merge. Spending still stops at the exact database UTC deadline and independently confirms live source before deducting points. Delayed close totals exclude entries at or after that round's boundary. Confirmed merge receipt, round result and cached winner retirement to merged/closed commit together; only unchanged open losing proposals carry into a future selection.

Technical validation must include proposal-specific implementation evidence. The trusted report binds the exact proposal manifest hash to declared canonical runtime/art paths whose hashes differ from the immutable base content manifest (new paths have null base hashes). Draft/master-only, unchanged paths and unrelated runtime changes cannot satisfy this gate. A valid unchanged baseline plus human Boolean approval cannot make an idea technically ready. Runtime promotion still requires actual supported schemas/mechanics and the separate human fight/determinism/UI/text evidence.

The scheduled Worker in `workers/community-rounds.ts` shares `GHOSTS_DB`; Pages does not run cron. `wrangler.community-rounds.jsonc` intentionally has merge automation disabled and no database ID. Bind the actual D1 database only during authorized deployment. Rounds last exactly seven UTC days; the epoch is `2026-01-01T00:00:00Z`. A round freezes at most one positively supported technically eligible winner, with admission time and PR number resolving ties. Unchanged-head support carries forward. A changed head requires re-review; the old ledger remains. A failed selected winner stays blocked, without a runner-up.

Create the repository-only App from `community-merger-app-manifest.json`, install it only on the content repository, and store `COMMUNITY_MERGER_APP_ID`, `COMMUNITY_MERGER_INSTALLATION_ID`, `COMMUNITY_MERGER_APP_SLUG`, and PKCS8 RSA `COMMUNITY_MERGER_PRIVATE_KEY` as Worker secrets/configuration. It needs Contents/PR/Checks write plus Actions read to verify trusted artifacts. The importer does not receive these credentials. The Worker alone may set `COMMUNITY_MERGE_ENABLED=true` after external proof.

Before enabling, inspect the actual active main rulesets. One restricts updates with the sole merger App bypass set to **For pull requests only**. A separate ruleset has no bypass, requires PR review and an up-to-date branch, and requires these four checks pinned to that exact App ID: `community/vote-winner`, `community/technical-ready`, `community/content-valid`, and `community/integration`. The merger emits them only after verifying the configured trusted workflow ID/path/digest/base, `pull_request_target` provenance, successful run, run-scoped immutable artifact digest, exact PR/head/rules/manifest identity, and frozen human attestation. Contributor-named GitHub Actions checks alone are insufficient. Approvals target the exact head and merge sends GitHub's expected SHA. Owners can administratively change rules; no owner lockout is promised. Merge never deploys.

Every selected winner additionally requires a pre-merge backup before checks, approval, or merge. An active tag ruleset must prohibit **update and deletion**, with no bypass actors, for `refs/tags/community-backup/*` (or all tags). Do not add a creation restriction that prevents the merger from creating a new restore point. Runtime verifies this actual ruleset alongside the main protections; a missing/weak tag rule stops the workflow.

The App creates a lightweight GitHub tag `refs/tags/community-backup/<SHA256(roundId)>` at the exact frozen current main/base commit. It never updates or deletes a tag. The service reads it back, verifies the exact commit and protection, and persists the manifest plus SHA-256 before emitting any required check. The manifest binds repository identity, round/operation ID, restore reference/base SHA, winner PR/head SHA, and human technical evidence hash. Repeated schedulers and lost tag-create or database-success responses recover the same immutable receipt. Every later approval/merge re-verifies the tag and rules. A moved base or changed tag blocks the selected winner without a runner-up.

This tag is a versioned restore point in the content repository, not an independent offsite backup. No storage provider or offsite durability is implied. An offsite export requirement needs a separately configured export and verification port; leave automation disabled until it exists and has actual evidence. Existing operator-retained full-repository backups remain separate from this tag workflow.

To verify a receipt, fetch the exact `manifest.reference`, compare `git rev-parse <reference>^{commit}` to `manifest.baseSha`, and compute SHA-256 over `backupManifestJson(manifest)` from `src/community/backup.ts`; it must equal `manifestSha256`. Inspect the immutable receipt from `/community/rounds/:id` or D1 and the actual tag rulesets. The tag reference uses only its fixed prefix and a hex digest; preserve the recorded manifest bytes/order when computing the digest.

Rollback is a separate reviewed operation: fetch the restore tag into a clean checkout, verify its commit and manifest digest, create a new rollback branch, restore the intended canonical data/art from that commit, regenerate/validate the runtime manifests, and open a PR through the protected review process. Never force main to the tag or move/delete the restore tag. A restored content revision still requires an explicit successful game deployment to change live gameplay. The merger does not perform rollback or deployment automatically.

Local audits use the durable file store, real SQLite SQL through a D1-shaped adapter, and actual local workerd/D1 in `scripts/community-workerd-audit.ts`. The workerd probe covers canonical credit/support rollback and immutable backup receipt persistence; its external GitHub port remains an isolated fixture. These probes do not claim production D1 deployment, installed App capability, actual protected merge, workflow execution for unpublished game code, or player acceptance. Run the actual deployed D1/API and repository policy probes before enabling. Required focused commands are the `scripts/community-*-audit.ts` files plus canonical-run service/settlement audits. The worker typecheck is `node node_modules/typescript/bin/tsc -p tsconfig.community-worker.json --noEmit`.

A merged idea/draft remains `merged` until a later actual runtime promotion is deployed. The pure validator is `src/community/release.ts`; no release action starts a deployment. `scripts/record-community-release.ts --store d1 --receipt <reviewed-receipt.json>` verifies the receipt and production D1/project binding without writing; add `--apply` to record through the actual D1 batch store. ## Operator doctor and guarded setup

`node node_modules/tsx/dist/cli.mjs scripts/community-automation.ts` runs a read-only doctor using `community-automation.config.example.json`. Copy that non-secret template to a local config and fill exact verified IDs/revisions/bundle path, then pass `--config <path>`. It checks actual repository identity, target-owner selected App installation and token scope, active main/tag rulesets, published trusted game commit/workflow digest and tooling variable, runtime build identity, explicit Cloudflare D1/project binding/schema, local Git history bundle, and Worker binding/secret metadata/cron. An absent or incomplete setup exits nonzero; it never substitutes the unrelated AI-wide installation. The default changes no credentials, rules, repositories, or deployments. The GitHub variable read may require an operator reader token with the relevant Variables read permission; no additional merger App write permission is implied.

Secrets are supplied only through environment variables (`COMMUNITY_MERGER_PRIVATE_KEY`, optional `COMMUNITY_READER_TOKEN`, `CLOUDFLARE_API_TOKEN`). The command does not inspect or refresh credential stores/OAuth scopes, print these values, or put them in generated configuration. `--write-config` writes a reviewable Worker config under `tmp/community-operator` with merge automation disabled, even when the report remains blocked. `ready` includes actual deployment/migration checks; `setupReady` separately allows safe setup of a not-yet-deployed Worker or wholly absent reviewed migrations.

`--configure-github` is a separate, explicitly mutating setup mode. It requires `COMMUNITY_SETUP_OWNER_TOKEN` with administrator access to the exact requested content repository, the merger App key, its correct selected WW installation, a published trusted game commit containing the candidate validator, and the configured approved workflow ID/digest/ancestry anchor. `mainUpdateRulesetId` identifies the existing main-only update lock (known bootstrap ID `25453489`). The command refuses broad/wrong-owner installations, unreviewed bypass actors, changed workflow bytes, missing published tooling or weakened backup protections before policy writes. It cannot install an App and never changes the unrelated AI-wide installation.

The mode creates and reads back a separate active no-bypass PR review/up-to-date/four App-pinned check ruleset **before** allowing the sole merger App PR-only bypass on the existing main update lock. It sets and verifies `TRUSTED_GAME_REVISION` through the explicit owner credential, confirms main has not moved, and verifies final actual rules. Existing generated check/review rules are preserved on replay; unknown policy shapes require review. A failed check-rule request or tooling-variable update leaves the existing main updater locked. Protected backup tags/rules are never changed. This configures GitHub policy only: no merge, deployment, game push, installation change or secret storage occurs, and the Worker merge flag remains false. Default doctor mode is still read-only. An optional `COMMUNITY_OPERATOR_READER_TOKEN` can supply separate Variables read permission for the doctor without adding that permission to the merger App.

The known main updater contains `update`, `deletion`, and `non_fast_forward` restrictions. Setup accepts and preserves those exact restriction kinds, including deletion/force-push protection; an unknown restriction or duplicate rule kind requires review instead of being removed.

`--apply --wrangler <trusted-wrangler-entry.js>` additionally requires `allowWorkerDeploy: true`, exact requested targets and every setup gate passing. It exports the actual remote D1 database into a private local SQL backup with SHA-256 receipt before executing only wholly absent migration files. Partial schemas require reviewed repair. It rechecks the remote schema, deploys only the scoped scheduled Worker with merge disabled, writes configured secrets through stdin, and rechecks actual deployment bindings/schedule. It never changes GitHub installations/rules or pushes/deploys the game, and it does not enable merging. This command has not been applied to production. Retained Git bundles cover committed history; working-tree snapshots and independent offsite exports remain separate operator backups.

## Private validation reads without a Pages App credential

Pages can bind `COMMUNITY_GITHUB_READER` to the existing `wandering-hand-community-rounds` Worker. The App private key remains solely in the Worker; do not add it to Pages variables or bindings.

The Worker's service-only `fetch` handler accepts GET requests from the internal binding origin only. Its allowlist is limited to the fixed content repository's workflow metadata/runs, run artifacts, artifact ZIP, PR metadata, immutable SHA comparison and the exact approved workflow source path at a40hex SHA. IDs, query names/values and repository are checked. It has no arbitrary URL, method, source-file, fork, Git ref, review, merge or upload proxy. The scheduled handler and disabled merge flag retain their existing behavior.

Before minting a token the Worker verifies the public repository ID/name/default branch, the configured App and selected installation on `wwang109`, and suspension status. The short-lived token stays in Worker memory, shared across concurrent acquisition, for at most ten minutes and never beyond expiry minus one minute; failure/expiry requires re-verification. It is not returned to Pages. This uses the already approved merger App's ability to issue a narrower read token, not a separate PAT or a new importer privilege.

The Worker downloads artifact bytes itself. Only the artifact ZIP endpoint may redirect, once, to HTTPS signed GitHub artifact hosts below `.blob.core.windows.net` or `.actions.githubusercontent.com`; the second request carries no Authorization/cookie headers and rejects further redirects. Returned responses contain only bounded bytes and fixed content-type/no-store/nosniff headers; upstream credentials, cookies, signed locations and error details are not forwarded. A response containing the active token or PEM is rejected. Pages still verifies workflow provenance, artifact SHA256, ZIP report identity and implementation evidence; the bridge grants no technical approval by itself.

## Recovering retained executors on a clean build

Production `scripts/run-executor-preflight.ts --production` reads the actual D1 approved executor registry, retaining each revision key **and its approved source digest**. Its default registry is the existing Pages project's `https://proof-of-concept-ab-deckbuilder.pages.dev/executor-archives/`; `RUN_EXECUTOR_ARCHIVE_REGISTRY_URL` may explicitly select another reviewed immutable HTTPS directory. Existing entries with final manifests are fully rechecked; corruption fails rather than silently fetching a replacement. The normal clean committed current-rules guard, immutable content SHA, fresh D1 export and bundle/asset limits still apply. Development contexts and arbitrary user-supplied revision keys cannot qualify as production archives.

The production generator prepares `public/executor-archives/<archiveId>/` for every approved retained executor plus the clean current executor. Vite's normal public-asset copy and the next explicit successful Pages deployment publish these immutable raw data files using the existing hosting provider. The preflight counts them in the asset-count/file-size gates. Stale unselected generated IDs are removed; selected directories must hash-match and contain only the expected closed source/art envelope and members. No server scripts, credentials or downloaded tooling are published or executed. Publishing current bytes does not approve them: only the guarded operator command below can change the D1 authority. A clean build retrieves missing approved contexts from the previous live deployment before assembling the next deployment, preserving that complete approved set.

An alternative export remains available: `node node_modules/tsx/dist/cli.mjs scripts/export-run-executor-archive.ts --output tmp/community/executor-registry`. It reads actual D1 approvals using `CLOUDFLARE_ACCOUNT_ID`, `D1_DATABASE_ID`, and `CLOUDFLARE_API_TOKEN`, exports exact approved revisions, refuses existing output directories and performs no remote writes. Another provider is optional. The Pages archive feature has not been deployed by this work; until an actual release publishes the files, missing required archives still fail closed. Keep D1 and the published archive set in the operator's backup/retention policy.

Each directory contains `archive.json` and `files/<repository-relative-path>`. The version-1 envelope is `{schemaVersion:1,archive,byteLengths,totalBytes}`. `archive` contains `{key:{contentSha,rulesRevision},sourceCommit,sourceDigest,archiveId,files,artFiles}`; maps hold path-to-SHA256 values. The canonical ID is SHA256 of `JSON.stringify({contentSha,rulesRevision})`. The D1-approved digest must equal SHA256 of `JSON.stringify({files,artFiles})`, and the rules revision must be exactly `<40hex sourceCommit>.<sourceDigest>`. Preserve map order when publishing: it is part of the existing digest. The envelope inventories exact byte counts and every downloaded file is hash checked.

The fetcher accepts only pure `src/engine`, `src/data`, `src/run` TypeScript/JSON, the root art manifest, and PNG/WebP below `public/game-art`. It rejects traversal, hidden/colliding paths, symlinks, external/missing imports and extra manifest fields. It streams with redirects disabled, a 1MiB envelope limit, 8MiB source-file/25MiB art-file limits, 2,048 files and 256MiB per archive, at most 32 contexts and 512MiB newly downloaded per preflight. All bytes verify in a sibling stage directory inside the cache first. Closed verified members enter the target through exclusive same-filesystem hard links; existing members must hash-match and are never overwritten. `manifest.json` is hard-linked last, atomically making the complete context available. An interrupted target without its manifest is unavailable and resumes safely on retry. An existing corrupt final manifest/context fails closed. Unsupported hard links fail rather than accepting a copied partial archive. No downloaded package, build script or tool is executed: the existing local trusted generator compiles only the approved source closure. A digest match proves identity with the approved registry; approving a new executable revision remains a trusted operator action, not a browser capability.

Windows sharing failures (`EPERM`, `EACCES`, `EBUSY`) or an in-flight conflicting member retry at most fifty times per member, with 100ms asynchronous waits. Other errors fail immediately; exhausted retries remove staging and leave no accepted executor. Windows namespace paths support long source/art names. This replaces directory renaming, which repeatedly returned EPERM on this host even outside the sandbox. A partial target may contain verified immutable members, but builders ignore it until its final manifest exists.

`scripts/run-executor-archive-audit.ts` proves export and recovery into an empty cache, real Windows child paths longer than260 characters, concurrent exclusive hard-link/final-manifest publication, interruption after two members followed by successful resume, conflicting bytes refused unchanged, transient sharing retries and bounded exhaustion/cleanup, distinct old/current source closures and verified cache reuse. Three repeated actual Windows runs passed after the hard-link change. Its HTTPS transport and D1 approval are isolated fixtures; no actual hosted archive retrieval is claimed.

## Registering the deployed current executor

`node node_modules/tsx/dist/cli.mjs scripts/approve-current-executor.ts` defaults to dry run and derives identity only from the generated **current** manifest. There is no arbitrary-key/digest argument. It verifies every cached and current source/art byte, source-closure digest, clean current Git revision, published game commit, exact published content-manifest hash, fixed existing Pages runtime rules/content/executor key, deployed archive envelope, explicit D1 identity and matching production Pages binding. Dirty/development/unpublished or mismatched deployments cannot be approved.

Add `--apply` to atomically insert the current approval or fill an existing null digest. The guarded upsert accepts only null or the identical digest, never overwrites a conflicting digest, preserves `active_references`, and verifies the returned approved row. Repeating the command is safe, including after a run's default unapproved registry row exists. `--wait` polls the fixed actual deployment identity/archive up to30 attempts with two-second waits before any D1 write; it never changes source or deploys. The requested future deploy command runs this after Wrangler confirms success, using the same explicit CF/D1 environment. If registration fails, deployment is not falsely reported as fully completed and the next production preflight remains blocked until verification succeeds. No client can invoke this command or grant points, and fetching a published archive never approves it.

`scripts/approve-current-executor-audit.ts` exercises real SQLite insert/default-null approval/idempotent replay/active-count preservation, conflicting and raced digests, bounded deployment polling and all clean/published/runtime/archive/D1 guards; static publication rejects unexpected extra files. `scripts/community-remote-release-audit.ts` exercises the operator REST adapter and both release SQL rollback boundaries through real SQLite, plus dry-run/no-write, wrong binding, missing deployment proof and receipt conflict/replay.
