# Battle passive pipeline plan

Scope: FOUNDATION IMPLEMENTED — finite generic pre-battle effects, static card/slot/build conditions, reference-only request contracts, and generated combat-log/API receipts. Talent/relic progression, production source catalogs, prices, targeting UI, saves, and dynamic hooks remain planned. Audit fixture magnitudes are illustrative capability probes, not actual item/talent content or approved production balance.

## Implemented foundation

`src/engine/passives/` exports strict validation/reference resolution, pure preparation, typed recipes/receipts, and generated descriptions. `PASSIVE_EFFECT_REGISTRY` owns each finite effect's fields, eligibility, application, and text; no handler branches on item/talent IDs. `CombatantSetup.passives` accepts an engine-owned schema-version-1 recipe; normal requests accept references, not arbitrary rules. Each source pins kind/id/version and each effect has its own id/binding. Source/effect order uses deterministic codepoint comparison, then target anchor order. Catalog lookup validates requested source/version existence; production ownership and budget validation remain adapter responsibilities.

Supported effects are `setupShield` (flat typed shield, once per source effect if any qualified card exists; unconditional automatic effects also work on an empty board), `cardShieldPower` (flat addition to every existing authored shield action on each qualified card), and `cardWeightReduction` (signed prepared per-card weight delta). None adds a new card action or changes geometry, identity, or saved definitions. Shield card scaling remains the authored card's normal scaling; gem-appended shields receive no passive bonus. Effective action power and passive source attribution are available in the shared derived card form.

Selectors support property/archetype; static predicates support anchor, occupied cell, and immediate nonwrapping footprint adjacency. Multi-cell cards count once. `playerCard` binds an optional opaque `BoardPiece.pieceRef` and follows that instance; `playerSlot` defaults to anchor matching, with explicit `match: 'occupies'` for a cell. Missing/unavailable selections produce inactive receipts; malformed recipes, out-of-board coordinates, duplicate references, overlap, unsafe integers, unknown fields, and unsupported effects are rejected. Recipes are copied and inputs remain unchanged.

`conditions.boardCount: { selector?, min, max? }` counts distinct active board instances against the unmodified tiered board snapshot. Duplicate catalog cards are distinct instances; a multi-cell card counts once; bag cards do not count. Counts never depend on contributions being applied, preventing effect-derived eligibility cycles.

`conditions.slotRange: { min, max, match? }` adds an inclusive zero-based board range. Its default anchor mode checks the leftmost card slot; `occupies` checks footprint overlap and still applies once per card. Thus authored `{ min: 1, max: 2 }` displays **Slots 2–3**. This is a board-slot range, not a travel-zone identifier. Ranges are validated against board width and never alter placement.

Preparation caches tiered cards; `resolveTieredSkill` then applies passive shield modifiers, effect gems, and canonical rider ordering once. Hero gems are still folded once by initialization. After event/context creation, `simulate` grants setup shields at turn zero through real `shieldGain` events, respecting the shared max-HP shield cap and logging wasted points plus `sourcePassive`. Modified shield casts carry `passiveSources` alongside the real card source. No fake gem/card origin, RNG calls, recursive hooks, or post-lethal callbacks are introduced. Empty recipes preserve baseline events.

Before setup shield events, the engine emits a turn-zero `preBattleEffect` event for every source effect, including inactive ones. Each event carries the evaluated receipt: pinned source, active flag/reason, affected card anchors and exact card references/footprints, selected binding, structured selectors/conditions, optional range, and generated conditions/effect/display text. `BattleLog.events` transports this same typed union through the battle API; renderers consume its generated text rather than independently evaluating rules or authoring duplicate copy. Empty recipes add no summary events. Production requests still cannot inject arbitrary recipes.

`BattleRequest.preBattle` is versioned `{ schemaVersion: 1, sources, bindings }`: source references contain kind/id/version; each selection identifies its source/effect and a card-reference or slot binding. Conditions/effect payloads are never accepted there. `resolvePassiveRequest` resolves pinned definitions through trusted `BattlePreparation.sourceCatalog`; the default catalog is empty, so unknown/unsupported references fail explicitly. Catalog selection removes preset target choices, and missing player choices remain inactive. Duplicate sources/bindings and unsupported fields are rejected.

Trusted `BattlePreparation.heroPieceRefs: [{ slot, pieceRef }]` maps portable references onto reconstructed occupied anchors, preserving duplicate-skill instance separation. Duplicate references/anchors and invalid geometry fail; a well-formed selected-card reference absent from the active board produces a target-unavailable receipt. Clients cannot claim ownership merely by sending a reference. A future owned-card adapter must distinguish foreign/unauthorized references from owned inactive cards. Slot choices need no instance mapping. The legacy trusted `heroPassives` seam remains for engine fixtures and cannot be combined with a reference request. Production catalog/owned-instance adapters remain future work; ordinary HTTP handlers use the same resolver with its empty default catalog. Trusted source `displayName` and resolved card names are carried into generated receipts; reference requests cannot supply names. [battle-passives-examples.md](battle-passives-examples.md) owns the closed playable development examples and their local endpoint.

Receipts carry generic `changes` with field, target, before/after, signed contribution, stage, and basis. Shield-power changes describe authored action power, not stat scaling. Starting shield changes describe actual capped typed pools after full hero-gem initialization. Weight changes describe starting aura/gem/prepared modifiers without future Slow/Burden taxes, and include unclamped `rawBefore/rawAfter`. Source contributions are attributed cumulatively in canonical order; each source reports its own transition, not a duplicate full final result. `describePassiveChanges` owns generated before/after copy for API, logs, and presentation.

The remaining sections describe the broader proposed system; dynamic hooks, tier promotion, appended keywords, healing modifiers, joint talent pricing, and service/save/ghost/UI adapters are not implemented by this foundation.

## Implemented generic slot weight reduction

The finite `cardWeightReduction` effect accepts a positive safe-integer `amount`, using shared selectors, bindings, and `slotRange` anchor/occupancy semantics. Each qualifying card receives the amount once per source effect, even when its footprint overlaps several affected cells. Compatible source reductions add. Static contributions last for that prepared battle; a temporary combat buff still needs a separate future duration/next-cast consumption hook and persistent use receipts.

Implementation contributes signed `passiveWeightDelta` through the existing aura/gem modifier bundle. `src/engine/combat/castSelect.ts` retains its final calculation: base `weightOf(skill)` plus modifier deltas plus current unit/card penalties, with one minimum of **1** after all additions. Saved/printed card weight is unchanged; reduced `SkillDef` weight is never prematurely clamped. Heavy/Lightweight, gems, and tax timing/consumption retain their existing seams.

Compact content direction is **“Cards in Slots 2–3: WT −X.”** Slot numbering is human one-based; `X` is an unapproved production magnitude placeholder. The shared registry generates the WT reduction token and common condition formatter specifies anchor/occupancy requirements. Opening source animation/target highlights can show the contribution, while structured API receipts carry actual prepared WT transitions. Card faces/details/previews must distinguish printed base WT from effective prepared/cast WT, including transient taxes; use unclamped prepared values before adding taxes and applying the final minimum.

Before authoring production sources, approve their magnitude, conditional scope, and PL price through the balance model. Capability evidence covers multiple sources, multi-cell overlap counting once, anchor versus occupancy, moves, gem/Heavy/Lightweight interaction, positive taxes at the minimum boundary, matching UI/API costs, and no benefit/use reset. No price or production values are selected here.

Goal: evaluate static build conditions once before battle, apply the resulting effective setup consistently, and check changing combat conditions only at supported safe steps.

Architecture: source-specific adapters produce typed, versioned contributions for a shared passive compiler and resolver. Pure preparation handles board/card/stat conditions; indexed generic runtime hooks handle state-dependent rules. The battle service is the authority for validated recipes and evaluation receipts; desktop/mobile render the same results without simulating.

## Current foundation and remaining integration

`src/run/resolveBattle.ts` validates/reconstructs the hero through `buildRequestHeroSetup`, builds foe setups, then calls `simulate`. Request validation lives in `src/run/battleRequestValidation.ts`; the dev/production entrypoints are `server/battleApi.ts` and `functions/battle.ts`.

`simulate` calls `initCombatState`, which calls `initCombatant` for each unit. With a nonempty passive plan, initialization uses `preparePassives` and its cached tiered skills through `resolveTieredSkill`; otherwise it uses the existing `resolveEffectiveSkill` path. Both paths check geometry, derive affinity, and fold hero-scope gems once. Shields initialize to zero; after creating its event array and context, `simulate` applies the compiled setup shields and emits turn-zero `shieldGain` events. `src/engine/cards.ts` owns tier/gem folding and canonical action ordering.

Remaining proposed integration: source-specific catalog adapters validate production definitions, versions, and budgets before producing engine recipes. A shared `resolveCombatantPreparation` facade may combine these adapters and current preparation for service/UI previews. Resolved values must never be fed back into an unprepared setup and folded again. Do not reinitialize a combatant to add passives. A distinct prepared-input variant is an alternative only if its type explicitly prevents further tier/gem resolution; do not introduce ambiguous raw-or-effective fields.

## Proposed phases

1. **Validate source recipe and selected bindings.** Pin equipment item/set versions, talent node/rank/card-recipe versions, relic instance/definition versions, and card definition versions. Validate ownership/trust facts, per-effect chosen card/slot bindings, talent prerequisite/exclusion/commitment rules, joint investment, equipment slots, and allowed trigger combinations. Binding validity precedes static-condition evaluation; catalog validity alone does not prove ownership in today's client-owned runs.
2. **Snapshot static board facts.** From the validated base board, record active card instances, leftmost anchors, occupied cells, family/property/archetype counts, and adjacency. Conditions use the linear zero-based geometry, not display rows. Multi-size cards count once. Snapshot excludes bag/held cards; distinguish `anchorSlot` from `occupiesSlot`. Identity/size changes remain excluded from the initial transform slice.
3. **Compile conditions and preparation.** Resolve static eligibility once and produce active/inactive contribution receipts with exact reasons. Select only supported pinned authored tier/replacement recipes. Apply one approved card-transform/gem pipeline; calculate shared stats and compatible direct-heal modifiers once. Proposal: authored tier/base-card transformations, existing gems once, then canonical rider ordering; approval, origin/scaling semantics, and incremental pricing are required before implementation. Validate the complete effective kit for target/scope/Splash compatibility. Preserve existing affinity, readiness, and card ordering rules.
4. **Initialize state, then emit setup effects.** Once state, event array, and context exist, execute supported generic setup contributions before turn 1. A setup shield needs a dedicated typed event or existing suitable shield event with explicit passive provenance, not an invented card cast or silent stat mutation. Add log/display support through the normal engine events, `scripts/fight.ts`/`scripts/logFormat.ts`, and playback models. Timing relative to any other setup effects must be explicitly defined and verified.
5. **Dispatch indexed runtime checks.** Static board predicates do not need a repeated all-source scan. Compile hook indexes for supported dynamic conditions. Only rules registered for the current step run, in stable order, against typed current-state context. Resolve before-cast, nonlethal-change, or end-turn hooks only when their precise timing contract exists.
6. **Finish combat normally.** Keep victory/loss selection and first-to-fall semantics. Return ordinary events plus passive evaluation/provenance data needed for display. Post-battle loot chances, card/event rewards, exploration forecasts, event costs, and irreversible-use settlement belong to `src/run`, not the combat loop.

## Dynamic hooks and safety

| Proposed seam | Intended condition | Required guard |
|---|---|---|
| Before an eligible cast commits | First eligible physical card cast; target/card qualification | Check actual eligible active card/action; do not consume on waiting, skip, or failed eligibility. Define use consumption and origin once. |
| After each supported nonlethal state change | Low-HP Emergency Ward | Preserve the existing potentially-lethal-step outcome check first. Dispatch only if battle continues and the receiving combatant is alive. |
| Explicit end-turn seam | A separately approved turn-state condition | Place relative to existing status ticks only after ordering is selected; never run after a terminal application. |

`src/engine/combat/simulate.ts` brackets potentially lethal steps with outcome checks, including ordered per-unit sweeps; `state.ts` exposes outcome/living-team helpers. An after-change hook cannot run merely after a whole cast: any earlier lethal application must terminate before passive callbacks. No post-killing-blow shield/heal, resurrection-by-callback, recursive self-trigger, or extra proc cascade. Bound each effect's once-per-battle/turn/target contract and use a stable receipt key; moving a card or rebuilding a preview cannot reset a consumed use.

These are proposed hook classes, not blanket authorization to implement every timing point. First slice should support static conditions, logged setup shield, and the shared direct-heal modifier. Dynamic first-cast and low-HP rules follow with their specific ordering evidence; do not add an unrestricted arbitrary callback system.

## Shared types, modules, and interfaces

### Selected targets in the compiled recipe

Per-effect definitions declare closed `targetBinding` modes `automatic`, `playerCard`, or `playerSlot`, with target scope, min/max count, and registered eligibility. Bound state is keyed by pinned source and stable effect/binding id; several effects share a choice only through an explicit group. Default interactive targets are active board instances/coordinates, never bag or held cards.

Card bindings identify owned instances and follow them on movement. Slot bindings identify coordinates and affect future eligible occupants; the effect declares whether it selects the anchor there or any card occupying that cell. Multi-size cards are single targets. Reject out-of-range coordinates, unknown/duplicate piece refs, illegal counts, and forged ownership facts; do not clamp or match by skill id. A once-valid card moved to inventory or removed becomes inactive until legally retargeted. Missing targets consume no use and do not auto-select replacements.

Current run cards carry `instanceId`, but `BoardPiece` lacks it. `battleRequestValidation.ts#heroCard`/`requestPieces` reconstruct only skill/slot/tier/gem references and currently discard instance identity. Proposed protocol: carry opaque recipe `pieceRef` tokens plus the owned-instance mapping through request reconstruction and compilation; verify uniqueness and target consistency without using slot/skill id as an instance substitute. Ghost/share codecs export stable local tokens and remap them on import, preserving repeated copies independently. This requires new request/save/codec support; it is not existing runtime identity, and client-owned data alone still does not establish authoritative ownership.

Unassigned required selections block purchase/retarget confirmation by default; existing unassigned/ineligible effects compile to inactive receipts rather than a universal battle refusal. Actual malformed/forged protocol references are validation errors. Any effect-specific battle-readiness blocking must be explicitly selected and described. Selection previews are scratch-only; pending fight/event recipes lock targets. Target changes/respec never reset persisted once-use facts. Runtime hooks receive only validated compiled bindings, not arbitrary client-selected ids to re-search every turn.

Proposed `src/engine/passives/types.ts`, `registry.ts`, `resolve.ts`, and `text.ts` own closed effect/condition unions, legal hook contexts, shared formatting, and deterministic combination. Talent/relic/equipment adapters retain their distinct purchase/acquisition/slot rules; the engine never switches on individual entity ids.

Proposed interfaces:

- `compileBattlePassives(recipe, baseBoard, catalogs): CompiledBattlePassives` returns static condition receipts, preparation contributions, and hook-indexed dynamic rules. Validation rejects unknown versions, conditions, action origins, and unsupported combinations rather than silently skipping them.
- `resolveCombatantPreparation(setup, compiled, skillCatalog): PreparedCombatant` returns effective skills/stats and evaluation receipts without mutation. Its boundary owns the existing gem fold; raw and resolved inputs cannot be confused.
- `dispatchPassiveHook(hook, context, compiled, uses): PassiveResolution` returns typed contributions, updated use receipts, and source-attributed events. The coordinator applies them at a defined safe seam; handlers cannot recursively dispatch another arbitrary hook.
- `describePassiveEvaluation(receipt, registry): PassiveDisplayModel` supplies generated clauses, requirements, active/inactive reasons, and source attribution from the same evaluation used by the service.

Each source records kind/id/version/instance or node-rank reference, effect index, unit/side, and target card reference where applicable. Preserve distinct passive origins: do not set `fromGem` on talent/relic actions. Multi-hit sharing, scaling, rider eligibility, and emitted calculation terms must have explicit origin semantics and pricing. Compatible equipment/talent/relic healing percentages add and floor once on the fully resolved direct heal amount before existing receiver processing; no independent per-source multiplication.

Use a documented canonical source order, then effect index and target anchor/unit order. Runtime use receipts are deterministic combat state, not wall-clock history. Source contributions cannot mutate saved owned cards or global catalogs. Empty passive input is neutral and introduces no combat RNG calls; future randomness needs its own approved seeded contract rather than incidental iteration-driven draws.

## Authority, previews, and persistence

Client prep displays the shared pure preparation model; the service validates and recomputes the same pinned recipe. Persist/materialize recipes before events or battles are committed. Both dev/production services and damage-band previews must agree. Keep no-equipment/no-talent/no-relic inputs compatible with existing requests.

Extend run saves, ghost capture/reconstruction, and share codes when combat features become active; refuse unsupported builds rather than silently dropping their passives. Pinned historical definitions must remain available. Generic run transaction hooks separately settle event/card/loot benefits with claim-once receipts; battle trigger checks cannot grant inventory or mutate event materializations.
